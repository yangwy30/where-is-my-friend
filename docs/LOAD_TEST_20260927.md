# 压力测试结果 — 2026-09-27

## 结论

普通数据量下，100 / 500 / 1,000 个虚拟用户同时初始化账号、刷新好友/计划/行程，业务请求均成功。高数据量下仍无请求失败，但 1,000 用户突发访问的好友计划接口 p95 达 **4.96 秒**，数据库连接等待拖慢了行程查询。

另外复现了一个真实的账号初始化竞态：**同一账号的并发初始化可能触发用户名唯一约束错误**。在高数据量最终运行的 400 次独立 SQL 调用中出现 22 次；临时数据库加入按认证账号的事务锁后，同样 400 次调用为 0 次错误，每个账号仍只有一份资料。候选修复未部署。

**本轮没有访问或修改生产数据库，没有更改航班套餐、额度或 App Store 提交，没有向真实用户发送推送。所有临时服务均已停止。**

## 测试边界

- 本机 Mac：M1 Pro、8 核、16GB；其他用户应用仍在运行，非专用基准机。
- PostgreSQL 17.10 独立进程，真实多连接；20 个业务连接，128MB shared buffers，4MB work_mem。SQL 和连接池等待分别限制为 6.5 秒，HTTP 客户端超时 20 秒。
- 实际路径：本机 HTTP → 当前生产 API handler → 模拟身份服务（25ms）→ 真实账号解析 SQL → 真实业务 SQL → JSON 响应。
- Apple 登录、Supabase Auth、Edge gateway、PostgREST 和公网网络未实测。推送签名/解密和 APNs 使用本机测试替身，模拟接收延迟 50ms。
- HTTP 连接逐步预热；这是业务负载基准，不是公网冷连接风暴测试。初期未预热连接/短空闲超时产生的 `ECONNRESET` 已识别为测试连接干扰，相应大规模突发结果不作为容量结论；最终高数据量运行将本机连接空闲超时设为 180 秒后，运输错误为 0。
- 以下 p95 是 **95% 单个 HTTP 请求的完成时间**，不代表整次 App 启动耗时。无法据此保证生产环境支持 1,000 人同时在线。

| --- | ---: | ---: |
| 已有合成账号 | 1,000 | 1,000 |
| 每人好友数 | 20 | 100 |
| 每人个人计划数 | 3 | 10 |
| 好友关系 | 10,000 | 50,000 |
| 个人计划 | 3,000 | 10,000 |
| 计划分享授权行 | 60,000 | 1,000,000 |
| 共同行程 | 600 | 600 |
| 航班记录 | 3,000 | 3,000 |
| 历史同城事件 | 5,000 | 5,000 |

每个已有账号参与 3 个行程，每个行程 5 人。注册阶段另外增加 100+500+1,000 个不同账号，因此后续刷新场景的数据库内共有至少 2,600 个账号。

## 结果

### 不同账号同时初始化

下表是模拟完成身份验证后的应用账号初始化，**不是 Apple 登录服务容量**。

| 同时初始化账号数 | 普通 p95 | 高数据量 p95 | 两次运行失败数 |
| --- | ---: | ---: | ---: |
| 100 | 94ms | 87ms | 0 |
| 500 | 200ms | 216ms | 0 |
| 1,000 | 363ms | 380ms | 0 |

### 已有用户同时刷新

每个虚拟用户依次请求 Friends、Friend plans、Trips 三个接口，所有用户同时开始。

| 虚拟用户 | 每次运行请求数 | 普通混合请求 p95 | 高数据量混合请求 p95 | 两次运行失败数 |
| --- | ---: | ---: | ---: | ---: |
| 100 | 300 | 125ms | 687ms | 0 |
| 500 | 1,500 | 245ms | 2,405ms | 0 |
| 1,000 | 3,000 | 427ms | 4,691ms | 0 |

1,000 用户高数据量场景的分接口结果：

| 接口 | p95 | 未压缩响应大小 p95 |
| --- | ---: | ---: |
| Friends `/v1/bootstrap` | 649ms | 40KB |
| Friend plans `/v1/travel-plans` | 4,956ms | 331KB |
| Trips `/v1/trips` | 4,724ms | 13KB |

好友计划 RPC 的 SQL 执行 p95 约 **162ms**，但获取数据库连接的等待 p95 约 **4,045ms**。Trip 列表 SQL 自身约 **6ms**，仍受到共享连接池排队影响。没有观察到数据库死锁。

这是优先分页/减少完整快照和请求重复的证据；仅靠增加连接数或提高配额不能保证改善，需要另行测量。

### 分散到一分钟内的刷新

1,000 个账号在 60 秒内各刷新 Friends 和 Friend plans 一次，共 2,000 次请求，约 **33.3 请求/秒**：

- 普通数据：0 失败，p95 **34ms**。
- 高数据量：0 失败，p95 **54ms**。

这与“1,000 个请求同时进行”不是同一概念；结果说明错峰能显著降低此测试条件下的排队。

### 并发正确性

- **同账号初始化缺陷**：普通运行的直接 SQL 竞态测试出现 19/400 个 `23505 app_users_username_key`；高数据量最终运行出现 22/400。并未创建重复账号，但部分调用会失败。单次 HTTP 32 并发未必复现，另一个校准轮次也曾触发，说明需要真实多连接回归覆盖。
- **本地候选修复**：在 `wif_ensure_app_user` 初次查找账号前，按 Auth UUID 获取事务级锁。高数据量的同样 20 轮 × 20 并发全部成功。测试后恢复原函数；未修改生产或正式迁移。
- **同一计划并发编辑**：16 次请求使用同一 revision，结果为 1 次 200、15 次 409，符合预期；这些显式冲突不是服务错误。

### 通知高峰

- 模拟当地 09:15，为 1,000 个合成用户生成早间提醒，三次调度分别生成 **500、500、0** 条；每次约 59–64ms，批次限制和去重生效。
- 另建 1,000 条可投递提醒，经过真实领取、权限准备与完成 SQL，再进入模拟 APNs 接收端。
- 5 轮各投递 200 条，全部完成，**0 重复、0 漏发**。单轮约 6–8 秒；此场景只有提醒队列，模拟 APNs 最高并发为 3。
- 测试连续调用 worker，**不能把这个耗时解释为线上送达时间**。生产定时任务每分钟一次，5 轮通常需跨越约 4–5 分钟，另加排队、供应商和设备因素。

## 建议顺序

1. **P1：修账号初始化竞态。** 已有可复现测试和本地验证的候选方案，下一步做正式迁移及回归后再部署。
2. **P1：好友计划分页/按需加载，减少整包刷新。** 高数据量下会返回 1,000 条好友计划，当前整包读取是明确的延迟和数据量来源。
3. **P1：前台刷新错峰与共享调度。** 保留已有请求合并，避免重新进入前台时重复读取。
4. **后续：同生产规格的专用 staging 公网压测。** 覆盖真实 Auth / gateway / PostgREST、冷启动、限流、实际 CPU/连接上限和跨区域网络后，才能确定线上容量与扩容点。

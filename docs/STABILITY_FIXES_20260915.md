# 审计问题修复 — 2026-09-15

本轮实现 `PROJECT_AUDIT_20260915.md` 的五项修复。未部署 Supabase、未修改定时任务、未上传 TestFlight，也未改构建号。城市群级匹配仍关闭；图标复用与地理同城身份保持分离。

## 1. 城市身份

- 新的 presence key 为 `v2|国家|行政区|城市`。国家、城市或行政区缺失时返回未知，不把同国同名城市猜成同一城市。
- Swift 与 SQL 使用一致的大小写/字母数字规范化规则；美国州全称到缩写的映射与区域目录配套，支持 California/CA、Texas/TX、New York/NY 等。
- 当前好友卡片、同城卡片、历史页面的当前停留、Widget 及预览都使用有行政区和新鲜度保护的判断。
- 历史事件增加可选 `cityKey`。旧格式/不同州事件仍可保留为历史，但不能被重新展示为当前同城通知。
- 只有 Core Location 的 locality 可被发布成城市。无法解析城市时不使用县或州代替，避免两个人在同一个州就被误判同城。
- 缺少必要行政区的旧记录需要补全定位信息。如果系统仍无法提供足够的信息，保持未知，而不是保证刷新后一定能匹配。

## 2. 同城时效与升级

- 当前同城/新通知要求双方位置在过去 24 小时内，且不能超过当前时间一分钟。App 与 SQL 边界一致。
- 位置变旧不会自行关闭停留 session，也不会在下一次刷新时制造“离开后回来”；卡片和通知仍会因过期而停止宣称当前同城。真正换城、撤销分享等仍结束当前停留。
- 直接修复实际被调用的 `wif_evaluate_direction`；历史 `recompute_colocation_for_pair` 入口转发到同一个实现。
- 新迁移 `20260915020000_presence_identity_and_freshness.sql` 重建现有 key 而不触发事件；用与现有 friendship 绑定的基线防止第一次补齐行政区时重放已有到达。
- 迁移会让旧规则下尚未发出的同城通知退出待发送队列，保留事件历史。已送达 APNs 的消息无法撤回。
- 发送前新增 `wif_colocation_delivery_allowed`，重新校验当前位置、分享权限、好友关系、设备归属和事件身份；新增查询以最多三个并发批处理，避免一次突发二十个查询。
- Widget 使用真实的位置更新时间，不再把刷新其他资料的时间当作位置的新鲜时间。

## 3. 推送 App 路由

- 客户端注册/注销推送明确携带 Bundle ID；离线重试也携带同一个 App 身份。
- 服务端只允许正式/ staging 两个已知 App，并独立处理 sandbox / production APNs。Staging TestFlight 可使用 production APNs，同时保留 staging topic 和 URL scheme。
- 未携带 Bundle ID 的旧客户端沿用已有环境映射；旧 Staging TestFlight 仍需要升级，不能从旧请求中可靠猜测所属 App。
- 真机发布前仍需确认现有 APNs provider key 被允许为两个 Bundle ID 推送；单元测试不等于 APNs 真机验收。

## 4. 定位重试

- 将尝试过的定位和成功解析的定位区分开。失败/取消后，同一份仍有效的定位可以再次解析。
- 已经成功解析的重复样本可立即结束显式刷新，不伪造新的更新时间，也不等待超时。
- 保留 generation/账号隔离与旧异步结果不能覆盖新结果的保护。

## 5. 删除账号

- 网络/服务端失败显示“无法确认账号删除”提示，结束进度并允许重试。
- 删除有独立进行中状态，防止重复触发；期间不允许新的刷新或资料保存覆盖删除结果。
- 服务端已确认删除后，SDK 在清理本地会话之后发生的远端 sign-out 错误不再把已完成删除报告为失败。
- 新增单元和 Debug-only UI 失败场景；不使用真实账号执行删除测试。

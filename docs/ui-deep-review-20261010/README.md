## 1. 本轮设计与行为

同城内容从独立大卡片移入 Friends 页头，紧接 “You are in…” 城市状态：小头像组、朋友姓名/人数和更新时间，底部使用细分隔线。展开后直接显示朋友行，点击进入该好友详情。

- 默认折叠，只由用户点击展开。刷新、切页、切回前台、重放同城通知均不得自动展开。
- 同城人数与展开后的朋友来自同一组有效城市匹配；关闭同城提醒不应把仍同城的朋友从界面移除。
- 新鲜度使用参与匹配的双方城市观测中最旧的时间，避免仅展示朋友刚更新、却忽略自己较旧的位置。
- 辅助字号隐藏装饰头像，允许文字换行；同城入口、朋友行、收起动作分别有至少 48pt、56pt、44pt 的目标高度。
- 过期/已撤回分享的通知继续显示安全的历史或失效提示，不把过去的同城事件当成当前状态。

本轮实现见 [同城组件](../../WhereIsMyFriend/Shared/Components/SameCityMomentCard.swift)；设计规范见 [DESIGN_SPEC](../DESIGN_SPEC.md)。旧卡片的历史说明与先前“只手动展开”的验证记录仍保留在 [前一轮记录](../ui-fixes-same-city-manual-20261010/README.md)。

## 2. 审计方式与范围

采用代码审阅、纯逻辑/仓储回归、真实原生 XCTest 交互、屏幕截图和本地后端测试互相验证。区分以下三种结果：

1. **已确认并修复**：能给出具体触发条件与对应代码路径，并记录适用的单元/原生验证结果。
2. **过程中失败、后续通过**：保留中间失败、根因与复测，不把早期记录改写为成功。
3. **保留为设计决策/后续验证**：有明确体验成本或平台边界，但没有足够证据称为新的功能错误。

原生环境包括 iPhone 18 Pro / iOS 27.0 和 iPhone SE 第三代 / iOS 26.4.1 模拟器。覆盖英文、简体中文、最大辅助字号、明暗主题、Reduced Motion，以及 Demo 中可控的离线、失败与权限拒绝状态。

本轮没有为了测试而删除真实账户、给真实朋友发邀请、发送真实 APNs、修改生产数据库或部署后端。产品模拟器使用 Demo 数据；仓储失败与并发测试使用受控替身。它们能证明本地状态与交互规则，但不能替代真实设备、真实多账号和真实网络故障验证。

东京与 Palm Springs 的城市搜索用例使用在线 MapKit 结果，均已通过，不能归入本地 mock。这类公开城市查询不等于访问或修改生产账户、好友与旅行数据。

## 4. Profile 放弃修改：修复过程与最终通过

最初实现使用编辑器内字段状态和出现时初始化，运行中发现点击 Close 后确认框短暂出现又消失，同时输入恢复到原值。这是本轮运行发现的实质回归，不能仅因代码有脏状态检查就标为修复。

最终实现将每次打开时的草稿固定在父页面的 item sheet 中，去除重复出现时的字段初始化；确认状态也由该草稿持有。提示使用 NavigationStack 外的 `alert(isPresented:) { Alert(...) }`，退出通过父页面明确关闭对应 sheet，提示动作保持原生结构。中间尝试过新提示 API 和视图局部状态，但在这段弹层/键盘重建流程中仍出现动作回调失效；诊断用 trace 已移除。

`profile-stable-presentation` 轮次在 iPhone SE / iOS 26.4.1 上已跨过 **Keep editing 保留输入 → 再次 Close → Discard 关闭编辑器 → 重新打开恢复原已保存内容 → 未修改直接关闭**。截图和测试日志已确认这一子流程。

该组合用例最后仍标失败，失败点已经移到个人计划的测试假设：脚本先认为默认城市列表中一定有 Tokyo，随后又假设始终有最近城市。不同测试隔离环境并不保证这两条前提。最终脚本改为编辑已可用的受众选择，检查 Keep editing 保留选择、Discard 放弃选择；没有修改产品城市数据来满足测试。

后续 iOS 27 运行也已跨过 Profile 的保留/放弃/关闭/重开断言，再在上述个人计划列表假设处失败。历史轮次仍按 **整体组合用例失败、Profile 子流程通过** 保存。

`final-small` 与 `final-pro` 中最终受众草稿版本均完整通过：既验证 Profile 的保留/放弃/重开，也验证个人计划受众的 Keep editing 与 Discard。小屏整轮265项、Pro最后2项全部通过。

### 5.1 产品缺陷与脚本/fixture 问题分开记录

- Profile 最初丢失输入、提示消失或 Discard 不关闭是运行中真实观察到的产品回归，保留修复与失败证据。
- 个人计划脚本依赖“默认一定有 Tokyo / 最近城市”的前提不成立，是测试数据假设问题。最终改测实际可编辑的受众，不制造城市结果，也不改变产品默认城市数据。
- `testFriendRequestNotificationRestoresAndCanBeAccepted` 的旧预览 fixture 依赖启动时的 scenePhase 时序，可能在未进入 active 时错过注入。这不是已证明的生产通知丢失。测试改用 `-testReadableRequest` 建立可读请求，再通过真实 `app.open` 打开邀请 URL，继续验证冷启动恢复和接受结果；生产路由没有为此改成预览路径。
- `testWidgetPrivacyAndEdgeStates` 预期初态可见朋友，却继承了上一条 Profile 测试保存的 `hideAll`。截图和控件树显示 Widget 正确隐藏全部内容，证明产品遵守已保存隐私选择；失败来自测试未建立自己要求的初态。现通过真实 Profile → Widget 隐私 → Show names and cities 操作设置此用例前提，之后继续检查隐藏/空态，不重置或削弱产品隐私持久化。
- 初轮旅行提示报 “Multiple matching elements” 时，证据是原生可访问性树中的同名包装节点。脚本定位与提示动作结构做了调整，不依据该断言单独声称真实用户无法点击。
- `journeys` 原始39条 UI 为36通过、3失败。三处脚本/fixture修正后的对应测试均在 `final-small` 通过；原始失败不改写，用后续结果记录恢复。
- `journeys-summary` 另外保留了5条**未解决的运行时布局警告** `Invalid frame dimension (negative or non-finite)`。对应功能用例均通过，没有崩溃证据，不能写成“没有运行时警告”或“已经修复”。只读展开结果后已定位到旅行创建/编辑和三种航班输入流程，均发生在首次点名称/航班号输入框、键盘出现后的等待阶段。五条 issue 的源文件 URL 都为空；抽查旅行创建与已验证航班的活动树只有标题/时间，没有调用栈或源文件附件，因此尚不能归因为 App 或系统代码。只读检查两个表单的 frame 参数，没有发现显式负数、非有限固定尺寸或几何尺寸相减的依据；这也不能排除运行时布局问题。本轮不盲改已通过功能验证的表单，不继续扩大排查；若后续获得功能影响或可归因栈，再定向修复。具体测试与证据限制保存在 [results/runtime-warnings.json](results/runtime-warnings.json)。

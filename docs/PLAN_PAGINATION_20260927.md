## 修复内容

- `wif_ensure_app_user` 按 Auth UUID 获取事务级锁，避免同账号同时初始化时冲突于默认用户名唯一索引。
- 新增独立 v2 接口：好友首页概览、个人计划按需读取、好友计划游标分页（最多 50 条）。v1 继续返回完整数据，不会悄悄截断旧 App 的列表。
- 首页保留每位好友的下一份计划及总数，因此头像计划标记不受第一页范围限制。
- 好友计划列表、好友详情、单份计划详情各按需要读取；第二页之后的计划也能直接打开详情。
- 游标包含数据版本；分享范围、计划内容或好友关系发生变化时重新开始分页，避免旧页与新页混合。每次查询均保留好友、分享授权、屏蔽和到期检查。
- 同一数据版本刷新时保留已经加载的后续页；下一页重复触发被合并，追加时按计划 ID 去重。
- 页面数据仅保存在当前账号的内存中。移除/屏蔽好友会使旧页失效，重新添加不能复活旧分享；权限变化也不会使个人计划保存卡住。
- 个人计划及其完整分享名单改为打开管理页或城市选择器时加载；常规首页刷新不再携带这部分数据。现有个人计划本地缓存保留。
- 短时间重复概览请求有 15 秒去重窗口；好友计划视图的后台刷新使用 60–75 秒错峰。没有增加全局同步弹窗。

## 同条件压力复测

仍使用本机真实 PostgreSQL、20 个业务连接、1,000 个合成老用户、每人 100 个好友与 10 份计划、100 万计划分享授权行。身份服务/推送为测试替身，不能据此保证公网生产容量。

新流程主动计入额外的首页概览请求：一次突发浏览包含 **Friends + 概览 + 列表第一页 + Trips 共 4 个请求**；旧流程为 3 个。因此混合 p95 不属于完全相同请求组合，不能只看这个数值就宣称整体提速。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 1,000 用户突发请求数 | 3,000 | 4,000 |
| 非预期业务失败 | 0 | 0 |
| 好友计划接口 p95 | 4,956ms（完整列表） | 3,636ms（第一页） |
| 好友计划响应 p95 | 331,020 字节 | 12,306 字节 |
| 新概览响应 p95 | — | 79,274 字节 |
| Trips 接口 p95 | 4,724ms | 1,477ms |
| 混合请求 p95 | 4,691ms | 3,495ms |
| 整个突发场景完成时间 | 约 5.97 秒 | 约 6.17 秒 |
| 直接 SQL 同账号初始化冲突 | 22 / 400 | **0 / 400** |

列表第一页的数据量减少约 **96%**；概览加第一页合计约 92KB，仍少于旧整包 331KB。但完整四请求流程的总体完成时间没有缩短，首页概览仍是后续优化重点。

另外：

- 分散在一分钟内的 1,000 用户首页刷新（2,000 请求），0 失败，p95 **52ms**。
- 20 个游标页完整读回 **1,000 条**授权计划，没有重复或遗漏。
- 同一计划 16 次同 revision 编辑：1 次成功、15 次明确冲突，符合预期。
- 1,000 条模拟通知分 5 轮各处理 200 条，无重复、无漏发。
- 早间调度分别生成 500 / 500 / 0 条，去重正确。

3. **生产告警阈值。** 已有通知聚合健康数据，后续应针对最老待发任务、接口 p95 与失败率配置持续告警。

## 发布顺序与回滚

准备脚本：`scripts/trip-migration/deploy-pagination.mjs`。不带 `--apply` 时仅核对/备份线上函数并准备 SQL；带 `--apply` 才执行单个迁移。脚本校验两个被替换函数的源码指纹，保存原 SQL 和 API 包，并使用事务、锁超时和迁移账本。

授权后先部署迁移与 API，再上传客户端 24；否则新版客户端会遇到尚未提供的 v2 接口。不能先发布客户端。

旧 App 无需更新即可获得注册竞态修复；好友计划分页需要新客户端。回滚时先停用新客户端分发并评估已经安装的版本，再决定是否恢复旧 API；保留新 v2 兼容接口通常比直接回退更安全。不要删除新表/视图或伪造迁移记录。

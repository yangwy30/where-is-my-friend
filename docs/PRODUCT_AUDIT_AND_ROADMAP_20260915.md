# Across Us：产品审计与下一步功能 — 2026-09-15

## 结论

核心产品已经成形：城市分享 → 发现现在/未来同城 → 联系朋友，以及共同 Trips → 汇总各自航班。下一阶段最值得投入的是让新用户完成这条路径，并补齐退出、撤回和失败时的体验。

建议顺序：**手动城市兜底与隐私清理 → 邀请安装流程 → 未来城市入口与 Trips 退出/取消 → 中文与帮助 → 小范围验证约见功能。**

## 需要先处理的问题

### F1 · P1 · 拒绝定位后，缺少可用的手动当前城市入口

**证据：** `Features/Sharing/SharingView.swift:149` 的城市操作只有刷新定位；搜索当前应用的 `updateCurrentCity` 调用，用户界面只接入 `AppRootView` 的定位结果。`Core/PlatformServices.swift:169` 却提示可以手动选城；首页与商店文案也作了类似承诺。旅行计划里的城市选择器修改的是未来安排，不能代替当前城市。

**影响：** 不愿授予定位权限、定位失败或需要纠正城市的用户，无法从现有正式界面完成当前城市设置。

**最小改动：** 在 City sharing 增加“手动选择城市”，搜索后确认城市、国家和行政区；显示手动来源和更新时间，提供明确的“恢复自动更新”操作。

**验收：** 拒绝定位仍能设置城市；行政区进入当前同城身份；手动选择不会被后台结果覆盖；未来计划不改变当前城市。

### F2 · P2 · 退出/删除账号未覆盖新旅行模块的磁盘缓存

**证据：** `Core/TravelPlans.swift:112` 在断开账号时清空内存，但不删除 `:180` 写入的 UserDefaults 计划缓存。`Features/Trips/TripLibrary.swift:234` 切换账号时同样仅重置内存/文件引用，未删除之前的账号 JSON。`Core/AppStore.swift:230`、`:248` 的退出/删除成功分支只调用已有 SharedAppStateStore 清理，不包含这些独立存储。

**隔离复现：** 从当前源码提取原 `TravelPlanLibrary`，用合成账号和假 Repository 保存一条计划，再以 `userID: nil` 断开账号。结果为 `saved=true, signedOutMemoryCount=0, signedOutDiskCacheRetained=true`。临时数据随后清除。Trips 的文件残留为代码路径确认；没有删除真实账号来测试。

**影响边界：** 这是设备端清理缺口，不能据此宣称其他账号能读取这些数据，或云端账号删除失败。

**最小改动：** 增加按账号和环境清理的统一入口，覆盖计划、Trips、旧缓存和待提交队列。删除账号只有在服务端成功确认后才完成清理；处理在途请求，避免其随后把数据写回。

**验收：** 退出后旧账号磁盘缓存消失；确认删除后无残留；另一账号的有效数据不受影响；清理后旧异步结果不能重建缓存。

### F3 · P2 · 当前后端测试未全绿：新增邀请依赖没有注入测试环境

**证据：** `supabase/tests/trips-api.test.mjs:46` 去除 API import 后在独立环境执行，但 `:49–55` 未提供新增的 `wakeInvitationWorker`。Trips 邀请路由触发 `ReferenceError`，测试收到 500 而非 200。

**隔离确认：** 仅在 `/private/tmp` 的测试副本补充不执行网络请求的替身，此文件 **10 项测试全部通过**。实际 API 在 `supabase/functions/api/index.ts:3` 已导入依赖，因此这是已复现的测试环境问题，不能等同于线上邀请接口故障。

**最小改动：** 更新测试依赖，并覆盖唤醒失败时邀请仍已持久化、由定时任务补发的行为。原仓库测试未由本轮修改，完整后端结果仍应报告为 72/73。

## 功能优先级

### 1. 邀请安装流程 — 高优先级，关系到能否带来第二位用户

- 现状：Release 的 `WIF_INVITE_BASE_URL` 为空，使用的签名权限文件没有 Associated Domains；AASA 示例仍含 `TEAMID` 占位符。已有自定义链接、登录后恢复邀请和明确接受的逻辑。
- 补充：可分享的 HTTPS 邀请页、已安装时打开 App、未安装时下载入口、复制用户名/邀请码兜底、过期或错账号说明。
- 安装后可让用户重新点击原链接或输入邀请码；不要把“安装后自动恢复邀请”当作 Universal Links 自带保证。Universal Links 的网站关联和未安装时网页回退机制见 [Apple 官方说明](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html)。
- 验收：用两台设备走完“无 App → 安装 → 登录 → 接受 → 成为好友”；Trip 邀请保留账号绑定和明确接受。
- 依据：`Core/ClientReliability.swift:80`、`Features/Trips/TripCloudModels.swift:134`、项目 Release 配置、`App/WhereIsMyFriendTestFlight.entitlements`。

### 2. 首页常驻“未来城市”入口 — 高优先级，成本较小

- 现状：固定入口在 You → Travel plans；首页的 Manage my plans 只有展开 Together soon 才能看到，而无匹配时整张卡片隐藏。
- 补充：在 Your city 下方放一个独立的“未来城市 / 添加安排”入口；已有安排时显示下一座城市与日期。继续复用现有编辑器，默认仅自己可见。
- 验收：零计划、零匹配用户无需去个人设置即可创建计划；不为无匹配状态新增占位同城卡；不自动开放共享。
- 依据：`Features/Friends/FriendsView.swift:61`、`Features/Profile/ProfileView.swift:61`、`Features/TravelPlans/TravelPlansView.swift:376`。

### 3. Trips 的退出、取消与成员管理 — 高优先级，补齐完整生命周期

- 现状：可以创建、加入、完成和撤销完成，也能撤销尚未接受的邀请。已加入成员列表只有展示；未找到退出 Trip、移除已加入成员、取消或删除 Trip 的用户入口及对应 API。标记完成会保留人员与航班，不等于取消/撤回共享。
- 第一版补充：成员主动退出；创建者取消行程；创建者移除成员，并清楚说明航班、历史内容和访问权限如何处理。空的误建行程可提供删除。
- 验收：退出或被移除后不能再读取该 Trip；相关推送发送前重新鉴权；本人航班及共享副本按约定处理；旧缓存与深链不会继续显示有效共享。所有权转移可以后续再做。
- 依据：`Features/Trips/TripsView.swift:280`、`Features/Trips/TripPlanningSheets.swift:344`、`supabase/functions/api/index.ts:236` 起的 Trips 路由。

### 4. “我向谁分享了什么”总览 — 中优先级

- 现状：当前城市、未来计划、共同 Trip 各有自己的权限。暂停城市不会撤回已分享的计划或 Trips，这个产品规则可以保留。
- 补充：按好友查看“当前城市 / 未来安排 / 共同 Trips”的共享概览，并能进入相应管理页；暂停城市时简短说明作用范围。
- 验收：用户能解释自己关闭了哪类共享，以及还有哪些内容对谁可见。任何批量撤回都要让用户明确选择范围。

### 5. 补齐简体中文和帮助入口 — 中优先级

- 现状：已有中文资源，但 `Travel plans`、`Together soon`、`Save plan`、`Invite friends` 等新增关键文案不在当前翻译目录。部分动态字符串还直接以英文 String 输出，不能只补翻译文件。
- 补充：覆盖新模块、权限说明、错误状态、日期/人数单复数与 VoiceOver 标签；加一个 App 内帮助/反馈入口，可由用户主动附带版本和权限状态。
- 验收：中文系统完成邀请、计划与 Trips 流程时无成片英文；诊断不默认收集城市、好友名单或航班详情。
- 现有 Notification settings 已有设备注册状态和重试，应复用，不再创建第二套。

### 6. 轻量约见 / RSVP — 后续实验，最值得验证的真正新功能

- 触发：已有 Here together 或 Together soon。
- 最小内容：提出一个日期/时间和简短活动，对方接受、另选时间或谢绝；确认后可加入日历。
- 价值：把“发现重叠”变成“确定见面”。这是产品假设，尚无使用数据证明必须开发。
- 先让少量朋友使用现有 Say hello；确认他们经常有重叠却难以约成，再做这一小步。

## 暂时保持范围

- 城市群匹配：当前图标复用不代表同城合并，扩大匹配必须先定义边界和用户预期。
- 航班更新：已有最后检查时间、过期与配额提示；数据库设有全局每日 20 次后台查询、合计 50 次查询的成本上限。扩量前再评估更新覆盖和调度，不在本轮建议中直接提高费用。
- 完整聊天、社交动态、实时精确定位和更多平台暂不进入下一版本；先验证现有的好友与相聚流程。
- 现有 CI 已执行后端及 iOS 检查；应修复当前回归，而非重复建设另一套 CI。

## 建议拆成三轮

1. **可用与可信：** F1 手动城市、F2 缓存清理、F3 测试回归；完成真机登录、两种 App 的 APNs 和后台定位验收。
2. **激活与可控：** 邀请安装流程、首页未来城市入口、Trip 退出/取消/成员管理，同时补齐这些路径的中文。
3. **验证相聚价值：** 共享总览和帮助；跟踪首位好友建立、首份计划主动共享、重叠卡打开、Say hello 使用等最少量事件，再决定约见功能。不将城市明文和好友名单作为分析事件属性。

成功指标应从“功能数量”转为：新用户能否带来第一位好友、双方能否理解并完成分享、出现重叠后是否采取行动。当前没有足够的真实行为数据，本报告不虚构转化率或留存率。
